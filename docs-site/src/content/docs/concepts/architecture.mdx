mojo-rl is five layers. Each one is usable on its own — the physics engines
without the agents, the neural-network framework without the RL — and each one
has both a CPU and a GPU path.

<LayeredStack />

The bottom three layers are ordinary libraries that happen to live in an RL
repository. [`nn`](/nn/) does not import an agent; `physics3d` does not import a
network. That is worth knowing before you decide how much of this you are taking
on: using the physics engine to drive your own controller costs you nothing
above it.

Generic traits let the compiler specialize the whole pipeline for the target
device, which is why the same source produces both a CPU loop and a fused GPU
one.

## Package layout

```
mojo_rl/
├── core/           Traits, replay buffers, tile coding, metrics, logging
├── agents/         Tabular & linear algorithms (Q-Learning → linear SAC)
├── deep_agents/    Deep RL, one facade package per algorithm
│   ├── dqn/ c51/ ddpg/ td3/ sac/ a2c/ ppo/ ppo_discrete/
│   ├── redq/ redq_ofe/ mbpo/ tdmpc2/ dreamerv3/ dreamer4/
│   ├── alphazero/ muzero/ efficient_zero_v2/ zero/
│   ├── core/       Module/Trainer/agent traits + shared infrastructure
│   ├── training/   CPU/GPU drivers, BatchedEnv wrappers
│   └── primitives/ loss/ data/
├── nn/             Deep-learning framework (Module + Param)
├── physics3d/      MuJoCo-inspired generalized-coordinates engine
├── physics2d/      GPU-batched 2D impulse engine
├── planners/       Trajectory optimizers (MPPI, CEM, iLQR) + GPU tree search
├── math3d/         Vec3, Quat, Mat3, Mat4 (+ GPU variants)
├── render/         SDL3 renderers, Metal shaders, video recording
├── envs/           25+ environments + Gymnasium wrappers
└── experimental/   Research code — APIs may break
```

## Layer 1 — Environments

25+ worlds in pure Mojo, grouped by the physics behind them:

| Family | Members | Engine |
|---|---|---|
| Tabular | GridWorld · FrozenLake · CliffWalking · Taxi | grid |
| Classic control | CartPole · MountainCar · Pendulum · Acrobot | Gymnasium-matching |
| 2D physics | LunarLander · BipedalWalker · CarRacing | `physics2d` |
| 3D locomotion | HalfCheetah · Hopper · Walker2d · Ant · Swimmer · Humanoid | `physics3d` |
| 3D manipulation | Reacher · Pusher · Sawyer | `physics3d` |
| Arcade | Pong · Breakout · Space Invaders | native GPU engines |
| Emulation | Atari 2600 (6502 · TIA · RIOT) | CPU only |
| Board games | Tic-Tac-Toe · Connect Four · Go · Chess | — |

Plus 20+ Gymnasium wrappers, used mainly as correctness references: the native
environments are faithful ports, and the wrappers let both be run side by side.

## Layer 2 — Physics

Two engines, written from scratch, because the environments needed different
things.

**`physics3d`** follows MuJoCo's design: models defined at compile time as
bodies, joints, geoms and actuators; simulation state in generalized
(joint-space) coordinates. The pipeline is collision detection → constraint
building → constraint solving → integration, with CRBA for the mass matrix, RNE
for bias forces, a choice of PGS / Newton / CG / island solvers, and MJCF XML
loading.

**`physics2d`** is impulse-based and GPU-batched, with state in a strided
`[BATCH, STATE_SIZE]` layout so one kernel launch steps hundreds of
environments. It carries revolute joints, articulated chains, a slip-based tire
model for CarRacing, and LIDAR distance sensing for BipedalWalker.

## Layer 3 — Deep learning

[`mojo_rl.nn`](/nn/) — described in the project's own words as *"something
between Tinygrad and PyTorch"*. Networks are assembled from small reusable `Module`
blocks, each `Param` owning its own value and gradient tensors.

- **70+ primitives**: Linear, Conv2D, attention, LSTMCell, NoisyLinear, LayerNorm/RMSNorm
- **Combinators**: Sequential, Residual, Parallel, Repeat
- **Pre-built models**: ResNet, GPT, ViT, LSTM
- **Optimizers**: SGD, Adam, AdamW, with grouped multi-tensor apply
- **Automatic fusion**: MatMul+Bias+Activation and Conv2D+Activation collapse into single GPU kernels
- **Training**: supervised `Trainer` with AMP and CUDA-graph capture

## Layer 4 — Algorithms

Ordered by increasing sophistication:

| Tier | Algorithms |
|---|---|
| **1 · Tabular** | Q-Learning · SARSA · Expected SARSA · Double Q · Dyna-Q · SARSA(λ) |
| **2 · Deep value** | DQN · Double · Dueling · Noisy · C51 · Rainbow |
| **3 · Policy gradient** | REINFORCE · Actor-Critic · A2C · PPO |
| **4 · Continuous control** | DDPG · TD3 · SAC · REDQ |
| **5 · Model-based** | MBPO · TD-MPC2 · DreamerV3 · AlphaZero · MuZero · EfficientZero V2 |

Deep agents follow a **facade pattern**: one package per algorithm, each
exposing an `XxxAgent` over a trainer plus a shared training driver. Networks
arrive as compile-time parameters, so `SACAgent` does not know or care what
architecture it is optimizing.

Tier 5 splits once more. Most agents decide by evaluating a policy network;
TD-MPC2 and the zero-series decide by running a **search** at every step. That
search is not part of the agent — it lives in [`mojo_rl.planners`](/planners/),
written against callback traits, which is why the same MPPI implementation
drives a learned world model in production and a closed-form oracle in a test.

## Layer 5 — Training drivers

The drivers own the loop so the agents do not have to. They come in a matrix:

|  | Single env | Batched |
|---|---|---|
| **Off-policy** | `run_offpolicy_train` | `run_offpolicy_train_batched` |
| **On-policy** | `run_onpolicy_train` | `run_onpolicy_train_batched` |

each with CPU and GPU variants. `BatchedEnv` wrappers such as
`Phyics3dBatchedEnv` and `BatchedGpuDiscreteEnv` adapt an environment to the
batched interface. Everything an agent facade's `train()` does is select the
right driver and hand it the trainer.

## The through-line: every layer runs on GPU

The reason the layering matters is that it does not break at the device
boundary. On a GPU run, this entire sequence stays on-device:

```
env step → observe → network fwd/bwd → replay sample → target update
```

No host round-trips; the data never leaves the device. That is only possible
because the physics engine, the networks and the driver are all Mojo, compiled
together. On NVIDIA the whole loop can additionally be captured as a CUDA graph
and replayed, worth roughly **1.4×** on SAC.
