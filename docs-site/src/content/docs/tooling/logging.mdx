Training runs emit metrics through a `Logger`. Which logger you attach decides
where they go — nowhere, a CSV file, or a live dashboard.

```mojo
from noeira.core.logger import NoOpLogger, CsvLogger, RemoteLogger, CompositeLogger
```

| Logger | Destination |
|---|---|
| `NoOpLogger` | discards — the default |
| `CsvLogger` | a local CSV file |
| `RemoteLogger` | HTTP POST to [noeira cloud](/tooling/monitor/) |
| `CompositeLogger` | several loggers at once |

## Attaching one

Loggers are passed to `train` as a pointer plus a compile-time type parameter:

```mojo
var logger = CsvLogger("/tmp/run_metrics.csv", buffer_size=64)
logger.set_config("algo", "sac")
logger.set_config("env", "HalfCheetah")

_ = agent.train[L=CsvLogger](
    env, NUM_STEPS,
    logger=Pointer(to=logger).as_unsafe_any_origin(),
    print_every=50_000,
    diag_every=1_000,
)
logger.close()
_ = logger   # keep it alive past the pointer
```

The `_ = logger` at the end is not decoration — it extends the lifetime past
the raw pointer handed to the driver. Dropping it is a use-after-free.

## Two cadences

The drivers emit at two rates, and separating them is what keeps a long run's
log both useful and small.

**Driver cadence** (`print_every`) — the coarse progress signal: `avg_reward`,
`episodes`. Every 50,000 steps is typical for a 600,000-step run.

**Diagnostic cadence** (`diag_every`) — the full metric bundle for the
algorithm: `actor_loss`, `critic_loss`, `alpha`, `mean_q`, `train_steps`. Every
1,000 steps.

Reward alone tells you *that* something is wrong. The bundle tells you what:
a collapsing return with rising `mean_q` is value explosion; with flat `mean_q`
it is a policy problem.

## RemoteLogger

Streams to [noeira cloud](/tooling/monitor/) over HTTP as batched JSON POSTs.
The run is announced by `register()` — call it through `register_run` with a
`RunContext`, before step 0 — and ended by `close()`, which sends the finish.

```mojo
from noeira.core.dotenv import load_dotenv

var env_vars = load_dotenv()
var logger = RemoteLogger(
    server_url=env_vars.get("NOEIRA_CLOUD_URL", ""),
    run_name="SAC HalfCheetah (GPU)",
    buffer_size=64,
    api_key=env_vars.get("NOEIRA_CLOUD_API_KEY", ""),
)
logger.set_config("algorithm", "SAC")
logger.set_config("env", "HalfCheetah")
logger.set_config("n_envs", String(N_ENVS))
logger.register()   # or register_run(run, logger) — see noeira cloud
```

A logger that is never registered still registers lazily on its first flush,
so older drivers keep working — but a run that dies before that flush never
appears on the dashboard. New drivers should use a `RunContext` and
`register_run`; see [how a run is registered](/tooling/monitor/#how-a-run-is-registered).

Configuration comes from a `.env` file at the repo root, read by
`noeira.core.dotenv`:

```
NOEIRA_CLOUD_URL=https://cloud.noeira.ai
NOEIRA_CLOUD_API_KEY=...
```

`buffer_size` controls batching (default 200). Smaller means fresher charts
and more requests; 64–200 is the usual range. `logger.total_logged()` reports
how many points were logged.

The POST never happens on the training thread. `flush` serialises the batch
and queues it; a background thread in `noeira/io/http_sink.mojo` owns the
connection, sends in order, and sends a heartbeat when the run has been quiet
for a minute. There is no Python in this path.

:::caution[It needs the HTTP shim, and it drops rather than stalls]
The sender is a small libcurl shim: build it once per machine with
`pixi run build-http`. If it is missing, the logger says so once and drops
metrics from then on — training continues.

The queue is bounded. If the dashboard falls behind, batches are refused
rather than blocking training, and every refusal is counted. `close()` drains
the queue, joins the thread and prints the tally; without `close()`, whatever
is still queued at exit is lost.
:::

## `set_config`

Configuration keys are recorded once with the run, not per point:

```mojo
logger.set_config("algorithm", "SAC")
logger.set_config("hidden", String(HIDDEN))
logger.set_config("batch", String(BATCH))
logger.set_config("buffer_capacity", String(REPLAY_CAPACITY))
```

Worth being generous here. Comparing two runs six weeks apart is only possible
if the thing that differed was recorded.

## Metrics per algorithm

Each algorithm defines a metrics struct. Representative fields:

| Algorithm | Metrics |
|---|---|
| DQN | `loss`, `mean_q`, `epsilon`, `train_steps` |
| SAC | `actor_loss`, `critic_loss`, `alpha`, `mean_q`, `mean_next_q` |
| PPO | `actor_loss`, `critic_loss`, `train_steps`, `n_updates` |
| MuZero | policy / value / reward losses, search statistics |

The shared training drivers additionally emit `avg_reward` and `episodes` at the driver cadence.

## What to watch

Drawn from the failures documented across these docs:

**`mean_q` climbing without bound** — value explosion. LayerNorm the critic. Hit
by SAC on Humanoid, MBPO, and REDQ at high UTD.

**Return collapsing after early progress** — often a target-network problem. If
BatchNorm is involved, check that the hard copy carried the running statistics.

**Loss descending while return stays flat** — the model is learning *something*,
just not the task. Classic symptom of a misaligned target: prev-action
off-by-one in a world model, or termination/truncation collapsed into one flag.

**`train_steps` not advancing as expected** — check `updates_per_step`. At the
default of 1 with 32 environments you are training 32× less than intended.

## CSV for offline runs

```mojo
var logger = CsvLogger("/tmp/muzero_cartpole_metrics_gpu.csv", buffer_size=64)
```

Right for headless boxes, CI and anything you want to plot yourself. Several
examples default to it.
